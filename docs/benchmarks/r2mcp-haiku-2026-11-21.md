# Head-to-head suite v4: rampage vs radare2's MCP server (Haiku, 2026-11-21)

Part of the [accuracy benchmarks](../benchmarks.md). This page adds radare2's MCP server, `r2mcp`, as a third server
beside rampage and REA. It reports one pass of suite v4 through `claude-haiku-5-5`, set beside rampage's Haiku pass
on the same suite. Suite v4 and its fairness rules are described in [the v4 plan](../plans/agent-bench-v4.md).

## Agent runs on suite v4 (2026-11-21)

**Setup.** Both passes used:

- the same 20 tasks: neutral suite SHA-256 `f215246b…` and identical task-definition hashes;
- the same runner, Claude Code 2.1.330 with no setting sources;
- the same isolation checks: one MCP server, ToolSearch as the only built-in tool, and the stream's init event
  verified.

Each task ran once per server.

- **rampage** is 1.10.0 (`c911c27`), with its default tool groups and the analysis store off. Its pass
  (`haiku-v4-1.10.0`) was recorded earlier and was not rerun for this page.
- **r2mcp** is label `haiku-v4-r2mcp-2026-11-21`, with the harness at `6e66cab` plus the contamination-screen fix
  described below.

### Configuration

The server was started as `r2mcp -d pdg` over stdio, with no other flags. That gives r2mcp's default tool set:

- 43 tools, which Claude Code read across two `tools/list` pages;
- not read-only and not the minimal set;
- r2 plugins and radare2rc loaded;
- the default sandbox grain (`exec,socket`).

`-d pdg` makes `decompile_function` use r2ghidra, the decompiler radare2 users normally install. Without it r2mcp
falls back to `pdc`, radare2's built-in pseudo-decompiler. The agent can still switch with `use_decompiler`.

Some tools are absent by default. The run tools (`run_command`, `run_javascript`, `run_script`) need `-r`, and
r2mcp's own help calls them "dangerous", so they were left off as shipped. Without them the agent has no way to:

- run raw r2 commands;
- use ESIL emulation;
- use the write commands (`wx`, `wtf`);
- hash a range (`ph`);
- use zignatures or FLIRT.

The `sql` tool is listed but needs the separate r2xsql plugin, which was not installed. One run called it and got a
tool error.

**Isolation.** r2mcp got the same mechanism as REA. Each run gets a private directory outside the repository that
holds:

- `fixture.bin`, or `fixture.hex` or `fixture.srec` for record files;
- a `device.svd` copy for the SVD and lock tasks.

The prompt names these absolute paths. r2mcp's `open_file` takes `arch`, `bits`, `cpu` and `baddr`, which is enough
to map the raw Cortex-M images. Intel HEX and S-record files open through radare2's `ihex://` and `srec://` URIs,
which the agent has to know. Every run passed the init-event isolation check.

**Harness fix (scored by rescore, no new model calls).** The first scoring marked two r2mcp runs as contaminated:
`lock-binding-cm4-raw` and `svd-fields-set-cm4-raw`.

- **Cause:** the agent opened the staged `device.svd` with `open_file` and hexdumped it. The SVD's own header
  comment names its source directory, `tests/fixtures/bench-v4/src/`, which trips the screen's `bench-v4/` marker.
- **Why it never showed before:** rampage and REA parse the SVD and never print that comment.
- **Fix:** the screen now ignores a path fragment that the run's own staged files contain. The repository path and
  the other fragments still count.
- **Effect:** both runs were correct once rescored. The report's `rescore` block records the change.

No run was rerun.

### Why r2mcp missed

| Task | Class | What happened |
| --- | --- | --- |
| emulate-control-thumb-elf, emulate-mix-x64-elf | tool gap | r2ghidra's pseudocode was right, but there was no way to run the function. The 500- and 1000-iteration loops were beyond hand evaluation, so the model answered unknown. |
| emulate-libc-arm64-elf | tool gap | The model evaluated the hash step by step with `calculate` and ran out of turns (40). |
| emulate-wide-mips-elf | tool gap, plus a model slip | There was no emulator, and the model gave a hand-computed value instead of unknown. |
| libid-names-m0-elf, libid-names-m0-raw | tool gap | There was no signature matching in the default tool set. The model browsed functions by hand: 125 calls before the turn limit on the ELF, and unknown on the raw image. |
| patch-export-bin-cm4-raw, patch-export-srec-cm4-srec | tool gap | There was no tool that writes a file, and the model answered unsupported. On the S-record task it also opened the file as plain text, not through `srec://`. |
| patch-values-cm4-hex | tool gap | The model opened the image through `ihex://` and named both checks exactly: CRC-16/CCITT over 0x800–0x83F at 0x840, and CRC-32 over 0x800–0x13FB at 0x13FC. It could not compute the new values. |
| lock-rollback-cm4-raw | model slip | Three of four fields were right. `counter_register` was the right register mis-converted to decimal: 0x40070010 given, 0x40009010 expected. |

Two problems came from the harness or configuration, and both were found:

- the contamination false positive, fixed and rescored as described above;
- the paginated tool list, which Claude Code follows, so all 43 tools reached the model.

No rerun was needed.

Eight of the ten misses are tool gaps of the default configuration. r2mcp's `-r` flag would expose raw r2 commands,
which reach ESIL emulation, writes and hashing. A pass with `-r` would measure a different, less restricted setup.

### Where r2mcp did better

- **svd-status-readers-cm4-raw:** r2mcp was correct where rampage was wrong. It took 34 small calls, 21 of them
  `disassemble_function` on every candidate function.
- **Tool errors:** r2mcp had 1 against rampage's 19. r2mcp's tools take few arguments, and most accept free-form
  address expressions.
- **Speed and call counts:** r2mcp was a little faster on callconv-arguments-x86-pe (8.7 s against 12.3 s),
  type-indirect-offsets-arm64-elf (8.9 against 10.8) and svd-fields-set-cm4-raw (16.4 against 17.7). It used fewer
  calls on libid-names-m0-raw, but answered unknown there.

### Caveats

- This is one repetition with one model, Haiku only. Earlier Haiku passes moved by a few tasks from one
  pass to the next: rampage's two suite v3 passes, on nearly the same build, scored 19/21 and 17/21 strict. A
  difference of one or two tasks is within that noise.
- The rampage numbers are from an earlier pass on 1.10.0 with the same suite and Claude Code version. They were
  not run in the same session.
- r2mcp ran without `-r` and without r2xsql, as shipped. The emulation, patching and library-identification
  categories mostly measure that configuration's missing tools, not radare2's analysis.
- Wall times include whatever else the machine was doing, and the two passes ran at different times.
- The raw report (`target/bench/h2h/haiku-v4-r2mcp-2026-11-21/report.json`) and its transcripts stay local and are
  not published.

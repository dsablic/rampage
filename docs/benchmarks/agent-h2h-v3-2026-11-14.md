# Head-to-head agent benchmark, suite v3: rampage vs REA

Part of the [accuracy benchmarks](../benchmarks.md). It follows [suite v2](agent-h2h-v2-2026-11-05.md) and was run
on the 1.0.0 feature set (commit `4973a07`).

## Agent runs on suite v3 (2026-11-14)

Suite v3 has 21 analysis tasks in seven categories:

- calling conventions (32-bit PE);
- Go (a stripped Go binary: callers, struct layout, nested fields);
- MSVC C++ (RTTI hierarchy, vtable slots, catch types);
- semantics (what a small function returns for given inputs, x86 and ARM32);
- switch tables (PIC and non-PIC);
- symbols at scale (a stripped SQLite build);
- typing (fields written, indirect offsets).

Truth comes from sources, DWARF, symbols and harness runs of the owned sources
(`tools/agent-bench/v3/derive-truth.py`). Neither server's output was used as truth. One model,
`claude-sonnet-5-5` through Claude Code 2.1.323 with no user settings, answered each task through one MCP server
at a time:

- rampage: `rampage mcp`, default tool groups, persistent analysis store off;
- REA: commit `970969c` over headless Ghidra 12.2.

Each task ran 3 times per server. The runs were sequential, and the server that went first alternated per
repetition. No run was superseded or rerun, and there were no infrastructure failures.

The [machine-readable report](agent-h2h-v3-2026-11-14.json) and its
[derived views](agent-h2h-v3-2026-11-14-views.json) hold every run. `tools/agent-bench/v3/report-views.py` computes
the views from the JSON alone. Neither file holds answers, transcripts or binary contents.

### Disclosures

- **Suite timing.** Suite v3 was designed before several 1.0 features landed: MSVC metadata, Go runtime types, the
  DWARF type fallback and scale search fixes. Those features close gaps the suite exposed. The scores below
  measure 1.0 on the suite as it was first written; no task was changed after the features landed.
- **Shared decompiler.** rampage embeds Ghidra's decompiler, so on tasks that come down to reading pseudocode
  both servers show the model the same code. The differences lie in loading, metadata recovery, search and the
  tool surface.

### Headline

| | rampage | REA (Ghidra) |
| --- | --: | --: |
| **Correct, strict, all 21 tasks** | **57/63** | **61/63** |
| Correct, lenient format (an extra `"status":"ok"` field forgiven) | 59/63 | 62/63 |
| Category-averaged, strict | 0.929 | 0.976 |
| Without the semantics category (17 tasks) | 51/51 | 51/51 |
| Semantics (4 tasks) | 6/12 | 10/12 |
| Median tool calls per task | 2 | 6 |
| Median wall time per task | 10.7 s | 31.6 s |
| Total model cost | $4.15 | $7.37 |

Outside semantics, both servers answered every run correctly. rampage needed a third of the tool calls, and its
wall time was 2–4× shorter on most categories and up to 26× shorter on the Go and SQLite tasks, where REA spends
minutes in the Ghidra import.

### The semantics misses

All eight wrong answers, rampage's six and REA's two, are semantics tasks: "what does this function return for
these arguments". Neither server has an emulator, so the model works the loop out by hand from the pseudocode.
The decompiled code it worked from was correct in every run. For example, rampage's run 2 of
`semantics-wide-x86-elf` answered `0x00000022D27DBBBA`, while REA's run 1 answered the correct `0x00000022D27DCBBA`:
one hex digit apart, from equivalent pseudocode. Two of rampage's misses on `semantics-loop-arm32-elf` were the
right value with an extra `"status":"ok"` field (counted in the lenient row).

With 12 runs per server, the 6/12 vs 10/12 gap reflects the model's arithmetic variance more than any difference
between the servers. A function-evaluation tool that runs the code instead of asking the model to simulate it
would make these tasks deterministic for rampage; it is on the post-1.0 list.

### Smaller models (preliminary)

Two earlier single-repetition passes of suite v3 through `claude-haiku-5-5` are not part of this report and their
runs are not published. Before the DWARF type fallback landed, rampage scored 19/21 and REA 18/21. After it,
both scored 17/21 strict; lenient, rampage scored 20/21 and REA 17/21. rampage's median was 3 tool calls per
task against REA's 6. Treat these as indicative only.

### After 1.0: the two gaps re-run

Two changes after the tag targeted the gaps above: the experimental `evaluate_function` tool, which runs a function
on arguments with a p-code interpreter, and server instructions pointing Go struct layouts at `get_type`. The same
five tasks were then re-run on rampage alone (commit `01321b2`, same model, client and task definitions, 3
repetitions each, $0.52). These runs are not part of the head-to-head scores above, and REA was not re-run.

# Head-to-head agent benchmark, suite v2: rampage vs REA

Part of the [accuracy benchmarks](../benchmarks.md). It follows the
[first head-to-head run](agent-h2h-2026-11-05.md), whose small lookups left both servers near 100%.

## Agent runs on suite v2 (2026-11-05 to 2026-11-06)

Suite v2 has 15 harder analysis tasks in six categories:

- stripped C++;
- typing;
- multi-step investigation;
- scale (a 49.2 MB stripped Go binary);
- raw firmware;
- build diffing.

Each answer is checked by machine against truth taken from sources, DWARF, symbols, LLVM and Go disassembly,
or harness runs of the owned sources. Neither server's output was used as truth. One model answered each task
through one MCP server at a time: rampage's `rampage mcp`, or REA's MCP server over headless Ghidra. Each task
ran 3 times per server. The runs were sequential, and the server that went first alternated per repetition.

A fresh-context fairness review after the first full pass found that it had to be corrected:

- The scale fixture used a Go version Ghidra does not support.
- The diff question was ambiguous.
- The headline leaned on categories that favour rampage.

This report includes the corrections. Every superseded run stays in the
[machine-readable report](agent-h2h-v2-2026-11-05.json) with the reason it was superseded. The
[derived views](agent-h2h-v2-2026-11-05-views.json) give the headline, core-only and original-pass scores below;
`tools/agent-bench/v2/report-views.py` computes them from the JSON alone. Neither file holds answers,
transcripts or binary contents.

### Scale tasks: time to first answer in a fresh session

The scale fixture is Hugo v0.140.0 (Apache-2.0). It was built for linux/amd64 with `-s -w` using go1.23.4,
the toolchain of Hugo's official v0.140.0 release (read with `go version` from the upstream linux-amd64
binary).

- **Size:** 49,197,208 bytes, just under the 50 MB the spec asked for. The upstream release binary is 49.2 MB
  too.
- **Go metadata:** the pclntab is intact, as in any Go binary, and Ghidra 12.2's Go analyzers support this
  version.

Each run opens a fresh copy, so these are times to the first answer in a new session. A long-lived REA session
would import the binary once and answer later questions in about the "without the import" time.

| | rampage | REA (Ghidra 12.2, 16 GB heap) |

| Open and analyze, measured outside the agent (one run, 2026-11-05 evening) | 12.9 s | 2,355 s |
| Agent wall time per run, median (range over 9) | 18.7 s (13.1–32.2) | 821.8 s (727.7–2,029.2) |
| Longest single tool call per run (REA: the Ghidra import), median | 4.5 s | 800.5 s |
| Agent wall time without that call, median (range) | 15.8 s (8.6–22.4) | 26.1 s (15.9–66.4) |

REA's import time varied by almost 3× with host load:

- 708–801 s in the five REA reruns that started after 02:41 on 2026-11-06;
- 1,548–1,987 s in the four evening runs of 2026-11-05, while other agents were working on the same machine;
- 2,355 s in the measurement outside any agent.

The first, superseded scale pass used the go1.27.3 build. There Ghidra reported
`Untested Go version [1.27.3]` and `Missing Go bootstrap type info`, and named no function. REA answered by
parsing the pclntab by hand, scoring 6/9. That result reflects an unsupported toolchain, not Ghidra's handling
of stripped Go at scale, and it is not used.

### Failure analysis

For each task with a scored miss: what the agent tried, what went wrong, and which capability was missing. The
evidence comes from the transcripts under `target/bench/h2h/full-v2-2026-11-05/runs/`.

- **firmware-reset-cm3-raw (REA 1/3).**
  - In every run, REA's first `open_binary` used an architecture name the schema rejects (`ARM:LE:32:Cortex`
    or `arm:cortex-m3`).
  - The model then opened the image as `raw-binary` with `arm` and only ever called `read_bytes`. It never
    called a disassembler, and decoded Thumb-2 by hand. Two runs decoded a `movw`/`movt` pair or a store offset
    wrongly: one gave 0x038E3AD1 for 0x078E3AD1, the other 0x40100108 for 0x400FE108.
  - REA's raw loader maps `arm` only to `ARM:LE:32:v7` (`src/ghidra/GhidraRawBinaryLanguage.ts`). It offers no
    Thumb or Cortex-M variant, although Ghidra itself has Cortex language definitions.
  - The limit is REA's raw loader, not Ghidra. rampage disassembled the image with `inspect_raw_code` or
    `disassemble` and answered 3/3.
- **pointer-chain-arm64-elf (REA 1/2 scored; run 1 was a model fallback).**
  - In run 3, reading Ghidra pseudocode, the model reported one pointer hop, [16, 8], instead of [16, 16, 8].
    It treated `conn_read`'s argument as the structure that holds the field and missed the load of
    `conn->stats` at offset 16.
  - This was a reading error over pseudocode that left the intermediate load implicit, not a missing tool.
- **option-bit-x64-elf (REA 2/3).**
  - In run 3 the model guessed `--archive` from the strings and kept the guess after reading pseudocode that
    did not settle which flag bit belongs to which option. The fixture deliberately maps `--archive` to the
    code that opens the other file.
  - The `{name, bit}` table was never typed. Two of rampage's runs read it with `inspect_data`; the third read
    the mapping from decompiled code.
- **cpp-vtable-slots-norrti-arm64-macho (rampage 2/3, REA 2/3).**
  - Both misses had all four slot addresses right but added `"status":"ok"`, so the strict contract failed
    them. The lenient variant counts them.
  - REA also added the field in `cpp-virtual-call-x64-elf` r2, so it hit REA twice. That run is a model
    fallback and is out of the accuracy, but its final answer would also have failed strictly for the same
    reason.
- **cpp-virtual-call-x64-elf (REA 2/2 scored).** Run 2 was a model fallback. Its final answer had the right
  target plus the `"status":"ok"` field.

### Infrastructure failures and reruns

Rule: a run stopped from outside before it gives any answer is rerun once, whichever server it belongs to. Such
a run is out of both servers' accuracy, as are runs whose turns did not all come from the requested model. The
original stays in the JSON's `superseded_runs` with the reason and the evidence.

- **Model fallback (2 REA runs): `pointer-chain-arm64-elf` r1 and `cpp-virtual-call-x64-elf` r2.**
  - Claude Code's stream reported a safeguard refusal (`model_refusal_fallback`, category `cyber`) and
    continued on `claude-sonnet-5`.
  - These runs produced answers, from the other model, so they were not rerun. They are out of the headline
    and kept as failures under the harness's rule.
- **Outside kill (1 REA run): `scale-caller-count-x64-elf` r1 on the rebuilt fixture.**
  - The MCP connection closed at 22:43:31 on 2026-11-05, 1,581 s into REA's first Ghidra wait, and `claude`
    exited 143 (SIGTERM).
  - Nothing in the harness sent the signal; another agent on the shared machine is the suspected source. The
    run was rerun once, and the rerun was correct.
- **Client usage limit (8 runs, both servers): every rebuilt-fixture scale run that started from 00:53 on
  2026-11-06.**
  - Instead of a model turn, Claude Code emitted a synthetic message: "You've hit your 5-hour limit".
  - Each was rerun once after the limit reset. All 8 reruns were correct.

**Runs that overlapped leftover Ghidra processes.** The runner used to stop only `claude`'s process group.
REA's headless Ghidra starts its own group and is reparented when `claude` exits, so Ghidra JVMs from finished
REA scale runs kept running:

| Leftover JVM | Started | Parent run ended (orphaned) | Killed | Resident |
| --- | --- | --- | --- | --: |
| from run 26 (REA scale-callees r1) | 13:42:58 | 14:07:32 | about 15:01:55 | about 7 GB |
| from run 28 (REA scale-caller-count r1) | 14:07:59 | 14:35:16 | about 15:01:55 | about 7 GB |
| run 30's own detached JVM | during run 30 | 15:28:42 | 15:28:53 | – |

Runs 27–31 overlapped one of them. The JSON's reason gives the same windows as whole JVM lifetimes (13:42–15:01
and 14:07–15:01). Commit `39dfe46` fixed the runner from run 31 on: it now records every descendant of `claude`
during a run and stops the survivors.

I decided to rerun 27–31 at about 15:03, after the outcomes of runs 27–29 were known: two misses, a REA count
and rampage's hand-computed string address. That was a rerun decided after seeing results. So for accuracy the
original runs count, and the reruns count for timing only:

- **Runs 27–30 (scale):** superseded in any case by the rebuilt fixture.
- **Run 31 (REA call-chain r2):** correct both times.

rampage's original run-29 miss is not attributed to load. It is the first ranked gap below, and it is part of
the original-pass score of 43/45.

**Process watcher coverage.** No watcher for leftover JVMs ran during runs 1–25; the first leftover dates from

### Ranked rampage gaps

The gaps are ranked by observed failures and error cost in this suite, each tagged with the area of rampage it
concerns:

1. **Search and string addressing at scale (search).** rampage's one genuine wrong answer was in the original
   scale-string-function run:
   - `search` for functions referencing the string, and a plain text search, both stopped on
     `match_work_budget` with no hits.
   - `list_strings` returned the string inside one undivided run of concatenated Go string literals.
   - The model computed the address by hand, got it wrong, and named a neighbouring string's function.

   All three runs on the rebuilt fixture still hit `match_work_budget` on both searches before finding the
   answer another way. Go string data needs splitting at its references, and the default search budget needs to
   cover a 50 MB image.
2. **C++ class evidence on modern Mach-O (C++ evidence).** In all 3 field-layout runs on the arm64 Mach-O,
   `class_evidence` returned no classes and no RTTI classes. The likely cause is that it does not follow RTTI
   pointers stored as chained fixups: the default link mode, and the one this fixture uses, while the earlier
   class fixture is linked with `-no_fixup_chains`.

   The model fell back to disassembly. The task cost 8–11 calls and 9 tool errors, rampage's second-highest.
   rampage answered 3/3, but only because the agent worked around the missing evidence.
3. **Raw-image ergonomics (raw firmware).** Firmware was 3/3 but caused 20 of rampage's 40 scored tool errors:
   - `binary_info` and `language_metadata` refuse a headerless file;
   - `disassemble` rejected raw profile names until the model found a closed language ID;
   - `inspect_raw_code` and `inspect_sleigh` were called without required fields.

   In validation, one run also misread `movt r1, #1934` because Thumb immediates are printed in decimal.
4. **Silent argument handling (tool arguments).** `disassemble` ignores unknown fields such as `address` and `length`,
   and disassembles at the function entry instead. In field-layout runs 2 and 3 the model asked for
   `address: 0x100000538` and got code from 0x1000006d4, without any error. An unknown field should be refused,
   as `inspect_data` and `search` already do.
5. **Per-call output budgets on large functions (output budgets).** `function_summary` on
   `images.DecodeImageConfig` exceeded the 60,000-byte tool budget in every scale-callees run, in both
   passes. The model recovered with other tools.
6. **Deferred-schema misuse (agent ergonomics).** 19 rampage tool errors were calls made before their
   schema was loaded. Each was corrected on the next call because the error carries the schema.

The investigation and typing tasks showed no rampage failure. With the C++ evidence gap above, the claim that no
C++ capability was missing is withdrawn.

### Setup

- **Model and client:**
  - `claude-sonnet-5-5` through Claude Code 2.1.318 (`claude -p`), default effort, driven by
    `tools/agent-bench/claude-runner.py`.
  - Isolation, ToolSearch and `MAX_MCP_OUTPUT_TOKENS` (200,000) are the same as in the first run. Every run's
    init event passed the runner's checks, and no run called a tool outside its server.
- **Limits:**
  - 40 turns and 900 s by default.
  - The scale tasks had 60 turns. Their time limit was 3,600 s in the superseded pass and 7,200 s on the rebuilt
    fixture, because REA's import alone took 2,355 s outside the agent. No scored run hit a limit.
- **rampage:**
  - Release `rampage mcp` built at `095ef9a` (kept by tag `bench-h2h-v2-2026-11-05`; the same tree is `ed5eb2d` on main), with `rampage-worker` beside it and the default groups.
  - The later commits change only `rampage-eval`, the runner, tasks and docs. rampage was not tuned during this
    work.
- **REA:**
  - `morluto/rea` at `970969c` (6.8.0), reinstalled under `target/bench/rea/` with the first run's steps: the
    same commit, a lockfile with the same SHA-256, `npm ci --ignore-scripts` (730 packages) and
    `npm run build:cached`. `rea doctor` was healthy.
  - Node 24.22.1, Ghidra 12.2 with OpenJDK 25.0.5, and the complete tool catalog.
- **Two REA settings differ from its defaults, and both are recorded:**
  - `REA_GHIDRA_STARTUP_TIMEOUT_MS=3600000`. The 330 s default gives up before Ghidra finishes importing the
    scale fixture.
  - `GHIDRA_HEADLESS_MAXMEM=16G`. With the 2 GB default, Ghidra ran out of memory after 23 minutes.

  Both are the remediations REA's own errors name.
- **Rizin is not installed on this host.** REA's catalog advertises Rizin-backed tools (`execute_rizin_command`,
  `cutter_command`, `debug_with_rizin`), and agents called them 8 times across the passes; every call failed.
  - In the superseded caller-count run that answered `unknown`, the agent named Rizin as what it lacked.
  - A host with Rizin would give REA another way to name functions and to read disassembly, including for the
    raw firmware.
  - So REA was measured with part of its catalog unusable. This weighs against REA most on the tasks where its
    Ghidra path was weakest.
- **Tasks:**
  - The manifests are in `crates/rampage-eval/tasks/v2/`, and the prompts and scoring rules in
    `crates/rampage-eval/tasks/h2h/neutral-v2.toml`, with the first run's system prompt.
  - A test checks the prompts against both servers' vocabularies.
  - Addresses are those of non-PIE executables and Mach-O images, so both servers show the same ones. The
    libraries are asked about by exported name.
  - The diff question was reworded after the first pass (recorded in its `change` field), to "exported functions
    [that] had their own code changed … ignore differences that come only from relocated addresses".
- **Fixtures:**
  - `tests/fixtures/bench-v2/build.sh` builds the stripped agent copies and the unstripped twins, and
    reproduces every digest.
  - The scale fixture is built by `tools/agent-bench/v2/build-scale.sh` (pinned to go1.23.4) into `target/`.
    The upstream release binary was used only to read its Go version.
- **Truth:** `tools/agent-bench/v2/derive-truth.py` derives every answer and checks it against the manifests,
  from:
  - DWARF and symbols;
  - LLVM disassembly;
  - `dyld_info`;
  - `go tool objdump` via `go_graph.py`;
  - host runs of three owned sources.

  Re-deriving on the rebuilt fixture changed no scale answer.

### Scoring notes

- **Strict scoring:** the final JSON object must hold exactly the requested fields.
  - Integers may be `0x` strings where a task allows it.
  - Sets are compared without order, using `tuple_set` for pairs and edges. Ordered lists must match in order.
  - Each task's rule is in `neutral-v2.toml`.
- **Partial credit:** the Jaccard index of the answered and expected sets, defined before any run, for set
  answers only.
- **Lenient format:** a variant added after the review. It forgives only an extra `"status":"ok"` field. It is
  reported beside the strict score, never instead of it.
- **Rescores:** two no-model rescores (commits `481999f` and `8f1378a`) recomputed the summary and filled the
  lenient field. They changed no outcome.

### Limitations

- One model and one client, sharing the machine with other agents. Host load shows in REA's import times, and
  in one outside kill.
- REA was measured through its MCP tools without Rizin, so part of its catalog could not run (see Setup). An
  analyst using Ghidra directly could do more, and REA's Hopper and IDA providers were not used.
- 15 tasks × 3 runs is small. Single-run differences such as 2/3 against 3/3 are within run-to-run variance.
- The tasks were written by the rampage project. Truth is independent of both servers and the prompts were
  checked against both vocabularies. Even so, the categories lean towards what rampage was built around, such
  as RTTI evidence, pclntab names and `diff_builds`. The core-only view above is the fairer comparison.
- [`todo.md`](../../todo.md) records a suite v3 of tasks where Ghidra is strong.

### Reproduce

```sh
tests/fixtures/bench-v2/build.sh                 # owned fixtures (committed; reproduces the digests)

target/debug/rampage-eval agent-bench --suite v2 --label NAME --repeat 3 --cost-cap-usd 38 \
  --rea-ghidra-startup-timeout-ms 3600000 --rea-ghidra-maxmem 16G
python3 -I tools/agent-bench/v2/report-views.py target/bench/h2h/NAME/report.json VIEWS.json \
  target/bench/h2h/NAME/runs
```

This spends model usage. Raw streams stay in `target/bench/h2h/NAME/runs/` with mode 0600.

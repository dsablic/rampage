# Head-to-head agent benchmark, suite v2: rampage vs REA

Part of the [accuracy benchmarks](../benchmarks.md). It follows the
[first head-to-head run](agent-h2h-2026-11-05.md), whose small lookups left both servers near 100%.

## Agent runs on suite v2 (2026-11-05)

Suite v2 has 15 harder analysis tasks in six categories:

- stripped C++;
- typing;
- multi-step investigation;
- scale (a 50.6 MB stripped Go binary);
- raw firmware;
- build diffing.

Each answer is checked by machine against truth taken from sources, DWARF, symbols, LLVM and Go disassembly,
or harness runs of the owned sources. Neither server's output was used as truth. One model answered each task
through one MCP server at a time: rampage's `rampage mcp`, or REA's MCP server over headless Ghidra. Each task
ran 3 times per server, 90 runs in all. The runs were sequential, and the server that went first alternated per
repetition. The [machine-readable report](agent-h2h-v2-2026-11-05.json) holds every run's outcome, tool calls,
tokens, cost and wall time. It holds no answers, transcripts or binary contents.

### Scale tasks: open and analysis time

The scale fixture is Hugo v0.140.0 (Apache-2.0), built for linux/amd64 with `-s -w`: 50,639,008 bytes, with
its pclntab intact as in any Go binary. Each server's open and analysis time was measured outside the agent
runs on a fresh copy, and is embedded in the JSON under `attachments.scale_open_time`:

| | rampage | REA (Ghidra 12.2, 16 GB heap) |
| --- | --: | --: |
| Open and analyze, measured outside the agent | 2.1 s (`rampage --json function list`) | 1,233 s (`rea decompile`, the first Ghidra-backed query) |
| Longest single tool call inside the agent runs, median (range over 9 runs) | 2 s (2–15) | 1,253 s (1,214–2,214) |
| Agent run wall time, median (range over 9 runs) | 20.4 s (10.6–29.1) | 2,158 s (1,266–2,744) |

In 4 of REA's 9 scale runs, a second tool family started another Ghidra import partway through the run, which
cost about 20 more minutes. This happened with `inspect_native_instruction` and `search_bytes` on the callees
task, and with `search_strings` on the string task. On the two reruns and on string-task run 3, REA's first
Ghidra wait took 35–37 minutes, against about 20 minutes on the other runs. Nothing else was running at the
time, so this spread looks inherent to REA and Ghidra on this host.

### Failure analysis

For each task with a miss: what the agent tried, what went wrong, and which capability was missing. Failures
come from the transcripts under `target/bench/h2h/full-v2-2026-11-05/runs/`.

- **scale-caller-count (REA 0/3).**
  - Ghidra, through REA, recovered no Go function names from the stripped 50 MB binary. REA reported
    `Unknown Ghidra procedure name` for every Hugo symbol, and its `search_procedures` found nothing.
  - In two runs the model parsed the pclntab by hand, using `read_bytes` and `search_bytes`, to find the entry
    address. It then used `procedure_callers` and `resolve_containing_procedure`, which gave 6 and 4 callers
    against the truth of 7 (from `go tool objdump`). Some call sites fall outside any procedure Ghidra created.
  - The third run answered `unknown`. It tried `execute_rizin_command`, but rizin is not installed on this
    host.
  - rampage named the functions from the pclntab when it opened the binary. It answered 3/3 with
    `list_functions` and `xrefs` in 2–4 calls.
  - Missing in REA: Go symbol recovery for stripped binaries at this size, and complete call references.
- **firmware-reset-cm3-raw (REA 1/3).**
  - REA opened the image as `raw-binary`/`arm`. Its first `open_binary` in each run passed a Ghidra language ID
    the schema rejected.
  - The model then read only bytes (`read_bytes`) and decoded Thumb-2 by hand. Two runs decoded a
    `movw`/`movt` pair or a register-offset store wrongly: one gave 0x038E3AD1 for 0x078E3AD1, the other
    0x40100108 for 0x400FE108.
  - rampage disassembled the raw image with `inspect_raw_code` or `disassemble` and answered 3/3. It still
    needed a median of 9 calls and made 20 schema or profile errors across the 3 runs (see the ranked gaps).
  - Missing in REA: disassembly of a raw image without a defined function.
- **pointer-chain-arm64-elf (REA 1/3).**
  - Run 1 was a model fallback (below).
  - In run 3, the decompiler output led the model to report one pointer hop, [16, 8], instead of [16, 16, 8].
    It treated `conn_read`'s pointer argument as the structure itself and missed the load of `conn->stats` at
    offset 16.
  - Missing: no tool capability. This was a reading error over Ghidra pseudocode that left the intermediate
    load implicit.
- **option-bit-x64-elf (REA 2/3).**
  - In run 3 the model guessed `--archive` from the strings ("Likely --archive, but verify via code").
  - It then read pseudocode that did not settle which flag bit 0x08 belongs to, and kept the guess. The fixture
    deliberately maps `--archive` to the code that opens the other file.
  - Missing: the record table of `{name, bit}` was not typed. Two of rampage's runs read it with
    `inspect_data`; the third read the mapping from decompiled code.
- **library-diff-x64-so (REA 2/3).**
  - REA has no diff tool. The model opened both builds and decompiled the exports with `batch_decompile` in
    both.
  - In run 2 it added `calc_scaled_sum`, which only calls the changed `calc_scale`.
  - rampage used `diff_builds` and answered 3/3.
  - Missing in REA: build diffing.
- **cpp-vtable-slots-norrti-arm64-macho (rampage 2/3, REA 2/3).** Both misses had all four slot addresses right
  but added `"status":"ok"` to the object, so the strict contract failed them (see [Scoring notes](#scoring-notes)).
  This was a formatting slip, not a capability gap.
- **cpp-virtual-call-x64-elf (REA 2/3).** The miss was a model fallback (below). That run's answer was correct.

### Runner errors

Two REA runs failed as `runner_error`: `pointer-chain-arm64-elf` r1 and `cpp-virtual-call-x64-elf` r2.

- In each, Claude Code's stream reported a safeguard refusal (`model_refusal_fallback`, category `cyber`) on a
  model turn. The session then continued on `claude-sonnet-5` instead of `claude-sonnet-5-5`.
- The runner fails any run whose turns did not all come from the requested model, as it did in the first
  head-to-head run.
- Counted strictly, these two runs are REA failures. They are not evidence about REA's tools: the
  `cpp-virtual-call` run's final answer was correct.
- Without them, REA's strict score is 34/43, against 44/45 for rampage. No rampage run hit a refusal.

### Runs that overlapped leftover Ghidra processes, and their reruns

The runner used to stop only `claude`'s own process group. REA starts headless Ghidra in a process group of its
own, and Ghidra is reparented when `claude` exits, so Ghidra JVMs from finished REA scale runs kept running. Two
of them held about 7 GB each:

- The JVM from run 26 (REA, scale-callees r1) was orphaned from 14:07:32 until about 15:01:55, when it was
  killed.
- The JVM from run 28 (REA, scale-caller-count r1) was orphaned from 14:35:16 until the same kill.
- Run 30 (REA, scale-string-function r1) left its own detached JVM, which was killed at 15:28:53.

Commit `39dfe46` fixed the runner. It now records every descendant of `claude` while a run lasts and stops the
survivors afterwards. The fix took effect from run 31, because run 30 had already started on the old runner.

From each run's start and end time, five runs overlapped a leftover JVM:

- 27, rampage, scale-caller-count r1: correct.
- 28, REA, scale-caller-count r1: wrong.
- 29, rampage, scale-string-function r1: wrong.
- 30, REA, scale-string-function r1: correct, 3,186 s.
- 31, REA, call-chain r2: correct; its first 11 s overlapped run 30's JVM.

No run before 31 timed out or hit its turn limit. The two failures were a wrong count, which is the same
failure REA's later scale runs show, and rampage's wrong string reference (below). Neither is obviously caused
by the load, but wall times certainly could be.

All five runs were rerun after the full pass, whatever their outcome, with `--rerun` (commit `546b266`):

- The originals stay in the JSON under `superseded_runs`, each with a reason.
- Their directories moved to `runs/superseded/`.
- The `rerun` block records the commit and versions.

The reruns are the scored runs above:

- rampage scale-caller-count r1: correct.
- REA scale-caller-count r1: `unknown`.
- rampage scale-string-function r1: correct.
- REA scale-string-function r1: correct.
- REA call-chain r2: correct.

The superseded rampage scale-string-function failure is still an observed failure, and it heads the ranked
gaps below. No other run was rerun.

No later run had a leftover JVM:

- A watcher checked every 30–60 s for JVMs with parent 1 from 15:29 to the end of the pass.
- It caught only run 90's own Ghidra, which REA detaches while the run is still going. The new runner stopped
  that JVM when the run ended.
- No Ghidra process remained after the pass or after the reruns.

### Ranked rampage gaps

The gaps are ranked by observed failures and error cost in this suite, and mapped to the
[roadmap](../plans/2026-10-16-ida-ghidra-parity-roadmap.md):

1. **Search and string addressing at scale (Phase 6, scale).** In the superseded scale-string-function run,
   rampage gave a wrong answer:
   - `search` for functions referencing the string, and a plain text search, both stopped on
     `match_work_budget` with no hits over the 50 MB image.
   - `list_strings` returned the string inside one undivided run of concatenated Go string literals.
   - The model computed the string's address by hand, got 0x1a90444 instead of 0x1a9041a, and followed the
     references of a neighbouring string to `(*PageConfig).Compile`.

   The other three runs, including its rerun, answered correctly with `search` and `list_strings`, two of them
   adding `xrefs`. Go string data needs splitting at
   its references, and the default search budget needs to cover a 50 MB image.
2. **Raw-image ergonomics (Phase 4, firmware loaders).** rampage solved the firmware 3/3, but it cost the most
   calls and errors of any rampage task: a median of 9 calls and 20 of rampage's 41 tool errors.
   - `binary_info` and `language_metadata` refuse a headerless file.
   - `disassemble` with a raw request rejected profile names until the model found a closed language ID.
   - `inspect_raw_code` and `inspect_sleigh` were called without required fields.

   One entry point that accepts a raw image plus an architecture, and names the valid profiles in its error,
   would remove most of this. In the validation pass, a rampage run also misread `movt r1, #1934` because Thumb
   immediates were printed in decimal. Showing them in hex would avoid that.
3. **Per-call output budgets on large functions (Phase 6).** `function_summary` on
   `images.DecodeImageConfig` exceeded the 60,000-byte tool budget in all three scale-callees runs, in both
   summary and code views. The model recovered with `decompile` or `xrefs`. A callee list without the full
   evidence would answer this in one call.
4. **Deferred-schema misuse (agent ergonomics, Phase 3).** 19 of rampage's tool errors were calls made before
   their schema was loaded, with fields like `length`, `count`, `query` or a missing `at`. Every one was
   corrected on the next call because the error carries the schema. REA's arguments errors have the same cause.
   Shorter or more uniform argument names, such as `at` and `size` everywhere, would cut these.

Neither server needed a capability rampage lacks in the C++, typing, investigation or diffing tasks. rampage
answered them with `class_evidence`, `decompile`, `inspect_data`, `xrefs` and `diff_builds`. Phase 5 (analysis
depth) and Phase 7 (diffing) showed no failures here, which means these tasks do not yet stress them.

### Scoring notes

- **Strict scoring:** a run scores only when its final JSON object holds exactly the requested fields, as in
  the first run.
  - Addresses and constants may be integers or `0x` strings (`hex_integers`).
  - Sets are compared without order. Edges and pairs use the new `tuple_set` kind.
  - Ordered lists, such as the call chain and the firmware stores, must match in order.
  - Each task's rule is in `neutral-v2.toml`.
- **Partial credit:** defined before any run, and only for the 4 set-answer tasks: the Jaccard index of the
  answered and expected sets, with 0 for no answer. It is reported beside the strict score, never instead of it.
- **Extra fields:** 2 runs, one per server, gave the right vtable slots with an extra `"status":"ok"` field.
  They count as wrong, as the contract says.
- **Answer extraction:** replies ending in a JSON object after prose were scored the same way. rampage did
  this twice and REA three times; every other reply was the object alone.
- **Rescore:** after the reruns, a no-model `--rescore` recomputed the summary once, after a fix to how partial
  credit is averaged (commit `481999f`). It changed no run's outcome, and its `rescore` block lists none.

### Limitations

- One model and one client. Two REA runs were cut short by the client's safeguard fallback, which is outside
  either server.
- REA was measured through its MCP tools with its full catalog. Its Rizin-backed tools cannot run on this host,
  and an analyst using Ghidra directly could do more.
- The scale results for REA depend on Ghidra 12.2's Go support: it named no functions in this stripped
  binary. REA's two settings above were needed to finish the import at all.
- REA's wall time includes a fresh Ghidra import in every run, because each run opens a new copy. rampage
  also analyzes per run, but finishes in about 2 s.
- 15 tasks × 3 runs is small. Single-run differences, such as 2/3 against 3/3, are within run-to-run variance.
  The owned fixtures are small, and the tasks have short checkable answers. This is not a blind whole-program
  benchmark.
- The tasks were written by the rampage project. Truth is independent of both servers, and the prompts were
  checked against both vocabularies. Even so, the choice of questions may favour capabilities rampage was
  built around, such as RTTI evidence, pclntab names and `diff_builds`.

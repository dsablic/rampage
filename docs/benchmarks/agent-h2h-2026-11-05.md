# Head-to-head agent benchmark: rampage vs REA

Part of the [accuracy benchmarks](../benchmarks.md).

## Agent runs on the canonical tasks (2026-11-05)

One model answered the 20 canonical parity tasks through one MCP server at a time: rampage's `rampage mcp`, then
REA's MCP server over headless Ghidra. Each task ran 3 times per server, 120 runs in all, sequentially. The
[machine-readable report](agent-h2h-2026-11-05.json) holds every run's outcome, tool calls, tokens, cost and
wall time; it holds no answers, transcripts or binary contents.

### Setup

- **Model and client:** `claude-sonnet-5-5` through Claude Code 2.1.318 (`claude -p`), default effort, at most 40
  turns and 900 s per run, driven by `tools/agent-bench/claude-runner.py`
  ([how it works](../parity-scorecard.md#head-to-head-agent-runs)).
- **Isolation:** no API key was set, so the runner loaded no setting sources (`--setting-sources ""`) and removed
  and denied every built-in tool. Every run's init event listed only the one server's tools (39 for rampage, 234
  for REA), that server alone as `connected`, Claude Code's five built-in plugins, its built-in agents (unusable
  without the Agent tool), no skills, and slash commands only from the server's own MCP prompts (6 for REA, none
  for rampage). No hook events appeared. The runner fails any run where this does not hold; none failed.
- **rampage:** commit `8093b2e`, clean worktree, release `rampage mcp` with `rampage-worker` beside it, default
  groups (core plus `enable_tools`).
- **REA:** `morluto/rea` main at `970969c` (package version 6.8.0), built from source because the 6.8.0 npm
  release admits only Ghidra 12.1.x. Installed under `target/bench/rea/` with `npm ci --ignore-scripts` from its
  lockfile (963 entries, all from the npm registry with integrity hashes; 730 packages installed for this
  platform; install scripts of esbuild, frida and fsevents skipped) and built with `npm run build:cached`. Node
  24.22.1, default tool families, `REA_ANALYSIS_PROVIDER=ghidra`. `rea doctor --provider ghidra` was healthy.
- **Ghidra:** 12.2 PUBLIC (Homebrew) with OpenJDK 25.0.5, headless through REA's own launcher.
- **Tasks:** the 20 canonical manifests, scored against their frozen answer contracts. The prompts are the
  tool-neutral wording in `crates/rampage-eval/tasks/h2h/neutral.toml`: the three capability probes no longer
  name rampage's tool groups, and the two `libhelper` questions say their addresses are link-time addresses,
  because Ghidra rebases the shared object to 0x100000. The probes' truth is per server: decompile yes for both;
  local-variable rename and patch-and-export yes for rampage, no for REA. The frozen `capability-patch-export`
  truth (false) predates rampage's Phase 3.2 patch tools.
- **Runs:** for each repetition, each task, rampage then REA. Each run had a fresh private directory outside the
  repository with its own copy of the fixture named `fixture.bin`. A smoke run (2 tasks × 2 servers) came first.

### Scoring notes

- A reply is scored when it ends with one JSON object on its own line. 10 rampage and 8 REA replies put
  reasoning before the object; the rest were the object alone. The smoke run showed both servers' correct helper
  answers failing a strict whole-reply rule, so the rule was relaxed before the full run, the same for both.
- One rampage run (`cpp-multiple-inheritance`, repetition 1) was first recorded as a runner error. The model had
  called `enable_tools` without the `mcp__rampage__` prefix; Claude Code rejected the call and nothing ran, but
  the runner then treated any call outside the server as an isolation leak. The rule now fails a run only when
  such a call returns a result. All 120 results were recomputed from their recorded transcripts with the
  corrected rule, without model calls; only that run changed, to correct. The JSON's `rescore` block records it.
- Four rampage runs made such rejected unprefixed calls (`enable_tools`, once also `list_strings`), all on the
  C++ tasks, and recovered with the prefixed name. REA runs made none.

### Observations

- REA's tool list makes every request about 112,000 tokens long (a capability probe answered without any tool
  call read 112,272 cached tokens), against about 33,000 for rampage's default groups (33,297). Prompt caching hides most of the price (both servers' prefixes are written once and read
  after), but cache reads still dominate token volume: 28.7 M for REA against 4.9 M for rampage over the 51
  analysis runs.
- REA's wall time is mostly Ghidra: in the median REA run, 57% of the wall time is spent inside tool calls.
  `open_binary` usually takes about 5 s, and the slowest call, typically the first Ghidra-backed query that waits
  for import and auto-analysis, 5–10 s (about 18 s for the PE and 23 s for the Go binary). rampage's median run
  spends 32 ms in tools.
- REA needed many more calls where it has no direct tool: Go package functions (9 against 1: rampage names
  `main.*` from pclntab at load), C++ multiple inheritance (11 against 4) and Mach-O format questions (5 against
  1).
- rampage's C++ tasks are where its group gating shows: `class_evidence` is in the `types` group, so the model
  first enables it, and four of those runs first tried a bare tool name.

### Limitations

- One model and one client. Another model, prompt style or MCP client may rank the servers differently.
- REA is measured through its MCP tool surface with default settings, not Ghidra's own capability: an analyst
  or a script using Ghidra directly could do more, and other REA providers (Hopper, IDA) were not used.
- REA's wall time includes Ghidra import and auto-analysis on every run, because each run opens a fresh copy.
  rampage's analysis is also per run but takes milliseconds on these fixtures.
- The tasks are small owned fixtures with short, checkable answers; this is not a blind whole-program
  reverse-engineering benchmark, and 17 analysis tasks are too few to separate servers by small margins.
- Three runs per task show some run-to-run variance (REA's class-name task, wall time ranges); medians over
  three runs are not stable estimates. Tool durations are measured by the runner between stream events and
  include client overhead.
- Costs are as reported by Claude Code, including the cache-write premium; they depend on caching across
  consecutive runs, which the interleaved order gives to both servers alike.
- The Phase 0, 1 and 3.3 agent results (`gpt-6.1-sol` through the retired OpenCode adapter, rampage-specific
  prompts) are not comparable with these runs.

### Reproduce

```sh
cargo build --release -p rampage-cli -p rampage-worker
cargo build -p rampage-eval
# REA under target/bench/rea/src at 970969c: npm ci --ignore-scripts, then npm run build:cached,
# and target/bench/rea/install.json describing the install.
target/debug/rampage-eval agent-bench --label full --tasks all --repeat 3 \
  --report-json docs/benchmarks/agent-h2h-DATE.json --report-md /tmp/tables.md
```

This spends model usage. Raw streams stay in `target/bench/h2h/<label>/runs/` with mode 0600, and
`--rescore` recomputes a finished run from them without model calls.

# Head-to-head agent benchmark: rampage vs REA

Part of the [accuracy benchmarks](../benchmarks.md).

## Agent runs on the canonical tasks (2026-11-05)

One model answered the 20 canonical parity tasks through one MCP server at a time: rampage's `rampage mcp`, then
REA's MCP server over headless Ghidra. Each task ran 3 times per server, 120 runs in all, sequentially, with the
server that goes first alternating per repetition. The [machine-readable report](agent-h2h-2026-11-05.json)
holds every run's outcome, tool calls, tokens, cost and wall time; it holds no answers, transcripts or binary
contents.

An earlier full run with the same tasks, kept as the [superseded report](agent-h2h-2026-11-05-superseded.json),
is excluded: its client settings made REA's calls, tokens and time worse than a stock Claude Code setup would (see
[differences from the superseded run](#differences-from-the-superseded-run)). Its scoring was symmetric, and its
accuracy results were within one run of these.

Failures:

- **REA, `cpp-class-names` (2 of 3):** answered `Circle`, `Square`, `Printable`, missing `Shape`. The model
  searched Ghidra's defined-string inventory with regexes that do match `5Shape`, but that inventory never held
  the `5Shape` type-name string; in the correct run the model also read raw bytes with `read_bytes` and found it
  there. REA has no RTTI recovery tool; rampage answered all three runs from `class_evidence`. The superseded
  run failed the same way.
- **rampage, `objc-superclasses` (1 of 3):** answered `NSObject` alone, missing `Animal`. The model inferred the
  chain from strings and `inspect_data` instead of enabling the `types` group for `language_metadata`, which the
  two correct runs used.

No run timed out, hit the turn limit or failed in the runner. Every number here is from this run; nothing was
rescored or edited afterwards.

### Setup

- **Model and client:** `claude-sonnet-5-5` through Claude Code 2.1.318 (`claude -p`), default effort, at most 40
  turns and 900 s per run, driven by `tools/agent-bench/claude-runner.py`
  ([how it works](../parity-scorecard.md#head-to-head-agent-runs)). `MAX_MCP_OUTPUT_TOKENS` was 200,000 for both
  servers. ToolSearch was allowed, so Claude Code deferred both servers' tool schemas and loaded them on demand,
  its normal behaviour; every other built-in tool was removed and denied.
- **Isolation:** no API key was set, so the runner loaded no setting sources (`--setting-sources ""`). Every run's
  init event listed only the server's tools plus ToolSearch (40 for rampage, 235 for REA), that server alone as
  `connected`, Claude Code's five pinned built-in plugins, its built-in agents (unusable without the Agent tool),
  no skills, an empty memory directory, and slash commands only from the server's own MCP prompts (6 for REA,
  none for rampage). No hook events appeared and no call outside the server ran. The runner checks all of this
  per run; none failed. It also deleted Claude Code's per-project directory for each run's working directory,
  where spilled tool results are written (2 REA runs had one).
- **rampage:** commit `7b40eed` (tag `bench-h2h-2026-11-05-measured`; its code is identical to squashed commit `5ddb3fe` on main), clean worktree, release `rampage mcp` with `rampage-worker` beside it, default
  groups (core plus `enable_tools`).
- **REA:** `morluto/rea` main at `970969c` (package version 6.8.0), built from source because the 6.8.0 npm
  release admits only Ghidra 12.1.x. Installed under `target/bench/rea/` with `npm ci --ignore-scripts` from its
  lockfile (963 entries, all from the npm registry with integrity hashes; 730 packages installed for this
  platform; install scripts of esbuild, frida and fsevents skipped) and built with `npm run build:cached`. Node
  24.22.1, `REA_ANALYSIS_PROVIDER=ghidra`, `REA_MCP_TOOL_FAMILIES` unset (the complete catalog).
  `rea doctor --provider ghidra` was healthy.
- **Ghidra:** 12.2 PUBLIC (Homebrew) with OpenJDK 25.0.5, headless through REA's own launcher.
- **Tasks:** the 20 canonical manifests, scored against their frozen answer contracts. The prompts are the
  tool-neutral wording in `crates/rampage-eval/tasks/h2h/neutral.toml`: the three capability probes do not
  name rampage's tool groups, and the two `libhelper` questions say their addresses are link-time addresses,
  because Ghidra rebases the shared object to 0x100000.
- **Probe truth:** decompile is yes for both servers; local-variable rename and patch-and-export are yes for
  rampage. For REA either answer is accepted on those two. It has no dedicated tool, but its `native` family
  advertises `execute_rizin_command` and `cutter_command`, raw command runners whose descriptions say commands
  can mutate files, and whether they work depends on a rizin install this host lacks. REA answered no in all
  six runs, so a strict "no" would have scored the same. The frozen `capability-patch-export` truth (false)
  predates rampage's Phase 3.2 patch tools.
- **Runs:** for each repetition and task, rampage then REA on odd repetitions, REA then rampage on even ones.
  Each run had a fresh private directory outside the repository with its own copy of the fixture named
  `fixture.bin`.

### Tool errors and truncation

- **REA's 34 analysis tool errors:**
  - 9 were addresses the model gave in the link-time convention before switching to Ghidra's rebased one
    (`procedure_assembly`, `procedure_pseudo_code` on `libhelper`; the errors name the 0x100000 base).
  - 7 were arguments that did not match the tool's schema, typically after the model called a deferred tool
    without loading its schema first (one of them an `execute_rizin_command` call).
  - 7 were `list_architectures` reporting itself unavailable for the target.
  - 10 were `inspect_binary_layout` calls: 5 refused because its pwntools profile runs only on Linux x64, and
    5 with invalid input.
  - 1 was invalid `inspect_analysis_view` input.
- **rampage's 1 analysis tool error:** a `decode_file_range` call without its required `codec`, again from a
  deferred schema the model had not loaded. Two more rampage calls used a bare tool name (`enable_tools`) and
  were refused by Claude Code without running; they are not counted as server calls.
- **Truncation:** 2 REA results on the Go task (278.5 KB from `list_procedures`, and one `inspect_analysis_view`
  page) exceeded Claude Code's fixed 50,000-character limit. Each was replaced by a 2 KB preview, with the rest
  written to a file the model cannot read (Read is denied). `MAX_MCP_OUTPUT_TOKENS` does not change that limit;
  only a server can raise it per tool, through `anthropic/maxResultSizeChars` in its tool list. Both runs still
  answered correctly. rampage had no truncated results.

### Differences from the superseded run

The superseded run's scoring was symmetric, but several of its client and host choices penalized REA's
efficiency. Each was verified, and this run differs as follows:

- **ToolSearch:** denied in the superseded run, so every request carried all of REA's 234 schemas (about 112,000
  tokens) instead of loading them on demand. Allowed here for both servers. Median cache-read tokens per REA
  analysis run are 458,156 there and 32,072 here; rampage's are 68,853 and 10,696.
- **`MAX_MCP_OUTPUT_TOKENS`:** Claude Code's default (25,000) there, which cut two large Go results with an error;
  six capability-probe results over 50,000 characters were also spilled to unreadable files. Here it is 200,000
  for both servers, and truncations are counted. The 50,000-character spill limit cannot be changed from the
  client.
- **REA tools this host cannot run** (`inspect_binary_layout` needs Linux x64; the rizin runners need rizin)
  failed 34 calls there. Narrowing `REA_MCP_TOOL_FAMILIES` was considered and rejected: those tools share the
  `native` family with REA's working Mach-O, PE and ELF inspectors and `inspect_with_objdump`, and the setting
  selects whole families. It stays unset (REA's stock catalog). Tool errors are reported per server, and the
  probe truth accepts either answer where those runners matter. With deferred loading, host-caused errors drop
  to 5.
- **Server order:** rampage always ran first there; here the order alternates per repetition.
- **Refused outside calls:** there, an outside call counted as refused whenever it errored. Here it counts as
  refused only on Claude Code's "No such tool available" or permission-denial text; any other outside call fails
  the run. All five refused calls in the superseded run carried that text, so the rule does not alter its results.
- **Rescore block:** the superseded run's `rescore` block was spliced in by hand. `--rescore` carries the measured
  run's versions, time and protocol and writes the block itself. This run needed no rescore.
- **Init check:** it also pins the built-in plugin names, fails on a non-empty memory directory, and runs inside
  normalization rather than only behind a substring pre-filter.
- **Spilled results:** stray spilled-result directories under `~/.claude/projects/` from the superseded run were
  deleted, and the runner removes its own.

Preliminary smoke runs, each with 2 tasks and both servers, checked the runner:

1. `smoke1`: `helper-plt-result`, `main-return-x64-elf`, 1 repetition, 4/4 correct. Streamed output-token counts
   are partial, so usage comes from the result event.
2. `smoke-2026-11-05`: the same tasks. Two correct answers, one per server, failed a strict whole-reply JSON rule
   because they ended a sentence of reasoning, so scoring accepts one JSON object that ends the reply.
3. `smoke2-2026-11-05`: the same tasks, 4/4 correct, before the superseded run.
4. `smoke4-2026-11-05`, before this run: `go-package-functions` and `capability-patch-export`, 2 repetitions, to
   check deferred loading, the output limit, truncation counting and the alternating order. 8/8 correct.

### Scoring notes

- A reply is scored when it ends with one JSON object on its own line. 5 rampage and 7 REA analysis replies put
  reasoning before the object; the rest were the object alone.
- Server tool calls exclude ToolSearch and calls Claude Code refused. The runner measures tool durations between
  stream events.

### Observations

- With deferred loading, REA's large catalog costs little up front: 6,498 tokens in the median first request,
  against 3,839 for rampage. The remaining token gap comes from more calls and larger results.
- REA's wall time is mostly Ghidra: in the median REA run, 54% of the wall time is spent inside tool calls,
  mostly `open_binary` (about 5 s) and the first Ghidra-backed query, which waits for import and auto-analysis.
  rampage's median run spends 22 ms in tools.
- REA needed many more calls where it has no direct tool: Go package functions (8 against 1: rampage names
  `main.*` from pclntab at load), C++ multiple inheritance (8 against 2) and the `libhelper` call chain (8
  against 4).
- On the x64 and Mach-O format questions REA answers in 1 call, as rampage does.
- rampage's group gating costs it: the one wrong rampage answer skipped `enable_tools`, and two runs tried
  a bare `enable_tools` name first.

### Limitations

- One model and one client. Another model, prompt style or MCP client may rank the servers differently.
- REA is measured through its MCP tool surface with its stock catalog and default settings, not Ghidra's own
  capability: an analyst or a script using Ghidra directly could do more, and other REA providers (Hopper, IDA)
  were not used. Some of its advertised tools cannot run on this macOS host.
- REA's wall time includes Ghidra import and auto-analysis on every run, because each run opens a fresh copy.
  rampage's analysis is also per run but takes milliseconds on these fixtures.
- Results over 50,000 characters are replaced by a preview for both servers; here that affected only REA.
- The tasks are small owned fixtures with short, checkable answers. This is not a blind whole-program
  reverse-engineering benchmark, and 17 analysis tasks are too few to separate servers by small margins.
- Three runs per task show run-to-run variance (each server's single-task misses, the wall time ranges); medians
  over three runs are not stable estimates.
- Costs are as reported by Claude Code, including the cache-write premium, and depend on prompt caching across
  consecutive runs.
- The Phase 0, 1 and 3.3 agent results (`gpt-6.1-sol` through the retired OpenCode adapter, rampage-specific
  prompts) are not comparable with these runs.

### Reproduce

```sh
cargo build --release -p rampage-cli -p rampage-worker
cargo build -p rampage-eval
# REA under target/bench/rea/src at 970969c: npm ci --ignore-scripts, then npm run build:cached,
# and target/bench/rea/install.json describing the install.
target/debug/rampage-eval agent-bench --label full2-2026-11-05 --tasks all --repeat 3 \
  --report-json docs/benchmarks/agent-h2h-DATE.json --report-md target/bench/h2h/full2-2026-11-05/tables.md
```

This spends model usage. Raw streams stay in `target/bench/h2h/full2-2026-11-05/runs/` with mode 0600, and
`--rescore` recomputes a finished run from them without model calls.
